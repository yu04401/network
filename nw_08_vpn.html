第8章　VPN・暗号化 IPsec / TLS / SSL-VPN

公衆網の上に安全な通路を作る技術。設問は「何を守るのか（秘匿・完全性・認証）」と 「どこからどこまでを守るのか（区間）」の2軸で整理できる。 IPsec は拠点間、SSL-VPN はリモートアクセス、TLS はアプリケーション単位—— という守る区間の違いが、そのまま方式選択の理由になる。

8.1暗号技術の基礎 頻出

2種類の暗号方式

守る対象と使う技術

HMAC とディジタル署名の違いを押さえる。 HMAC は共通鍵を使うため、検証できるのは鍵を共有している相手だけであり、 両者が同じ鍵を持つので「相手が偽造した」可能性を排除できない＝否認防止にはならない。 ディジタル署名は秘密鍵を持つ本人しか作れないので否認防止が成立する。 IPsec や TLS の通信中の完全性検証には、高速な HMAC が使われる。

8.2IPsec の構成要素 頻出

IPsecは、IP層で暗号化と認証を行うプロトコル群。 上位のアプリケーションを一切変更せずに保護できるのが最大の特徴で、 拠点間VPNの標準となっている。押さえるべきは「2つのプロトコル」×「2つのモード」の組み合わせ。

AH と ESP

2つのセキュリティプロトコル
AH（Authentication Header）ESP（Encapsulating Security Payload）
プロトコル番号5150
暗号化しないする
完全性・認証する（IPヘッダも保護対象に含む）する（IPヘッダは対象外）
NAT越え不可。NATがIPヘッダを書き換えると完全性の検証に失敗するそのままでは不可（ポート番号がないため）だが、NAT-T で解決できる
実運用ほとんど使われない事実上こちらだけを使う
「秘匿が不要なら AH でよいのか」——理屈の上ではそうだが、 NATと共存できないという致命的な制約があるため、実際には ESP の認証機能のみを使う（暗号化なしのESP）か、 素直に ESP で暗号化する。試験では「AHはNATを越えられない理由」が問われる。

8.3IKE と SA の確立 頻出

暗号化するには、両者が同じ鍵と同じアルゴリズムを持っている必要がある。 それを安全に取り決めるのが IKE（Internet Key Exchange、UDP 500番）で、 取り決めた内容の集合を SA（Security Association）と呼ぶ。

■ 午後での問われ方
  • フェーズ1とフェーズ2で確立されるSAの名称と本数 → IKE SA（1本）／IPsec SA（方向ごとに1本、計2本）
  • PSKではなく証明書認証を採用する理由 → 「拠点数が多く、共通の事前共有鍵では 漏えい時の影響範囲が全拠点に及ぶうえ、鍵の配布・更新の運用負荷が大きいため」
  • PFSを有効にする理由 → 「鍵が漏えいしても、それ以前に記録された通信を復号されないようにするため」
  • アグレッシブモードを使う場面 → 接続元のIPアドレスが固定でない（動的に変わる）場合

8.4IPsec の設計論点 頻出

カプセル化オーバーヘッドと MTU

ESPトンネルモードでは、新IPヘッダ・ESPヘッダ・初期化ベクタ・パディング・ESPトレーラ・認証データが加わり、 合計でおおむね50〜60バイトの増加になる。NAT-T を併用すればさらに UDP ヘッダ8バイトが乗る。

MTU 1500 の経路で 実効的に運べるデータ量が減るため、そのままでは フラグメントの多発、あるいは DF=1 のパケットの破棄（PMTUDブラックホール）が起きる。 対策は第4章と同じく、VPN装置でのMSSクランプ、またはトンネルインタフェースのMTU設定。 「IPsec VPN 導入後に、特定の業務システムだけ動かない」という設問はこの筋で読む。

セレクタ

セレクタは、どの通信をIPsecで保護するかを定義する条件 （送信元／宛先アドレス、プロトコル、ポート番号）。 ここに合致した通信だけがトンネルへ入る。 両拠点でセレクタの定義が一致していないとフェーズ2が確立しないため、 設定不一致の典型的な原因になる。

GRE over IPsec 頻出

IPsec には ユニキャストのIPパケットしか運べないという制約がある。 そのため、マルチキャストを使うルーティングプロトコル（OSPFなど）を IPsecトンネル越しに動かすことができない。

DMVPN差がつくは、 ハブ&スポーク構成を基本としつつ、拠点間で直接通信が必要になったときだけ スポーク間に動的にトンネルを張る技術。 全拠点間をフルメッシュで事前設定する手間を省きながら、拠点間通信がハブを経由する遠回りを避けられる。

■ 午後での問われ方
  • IPsecトンネル上でOSPFを動かしたい → GRE over IPsec を用いる。 理由は「IPsecはマルチキャストを転送できないため、GREでユニキャストにカプセル化する必要がある」
  • VPN導入後に大きなデータの転送が失敗する → カプセル化によるMTU減少。対策はMSSクランプ
  • 拠点数が増えたときのトンネル本数 → フルメッシュなら n(n−1)/2 本。管理負荷の議論につながる

8.5TLS 頻出

TLS（Transport Layer Security、旧SSL）は、 TCPの上、アプリケーションの下で動作し、アプリケーション単位で暗号化・完全性・サーバ認証を提供する。 IPsec が「経路まるごと」を守るのに対し、TLS は「この通信だけ」を守る。

ハンドシェイクの流れ

TLS1.2 と TLS1.3
TLS 1.2TLS 1.3
ハンドシェイク2往復（2-RTT）1往復（1-RTT）。再接続時は 0-RTT も可能
鍵交換RSA鍵交換も選択可能ECDHE などに限定＝PFSが必須になった
暗号スイート脆弱な方式（RC4、3DESなど）も含む安全なものだけに絞り込み、選択の余地を減らした
秘匿範囲証明書などが平文で流れるハンドシェイクの大部分も暗号化される

SNI 頻出

SNI（Server Name Indication）は、 ClientHello に接続したいホスト名を入れて送る拡張。 サーバはTLSハンドシェイクの前にはHTTPのHostヘッダを読めないため、 これがないと1つのIPアドレスで複数のドメインを扱う（バーチャルホスト）際に、 どの証明書を提示すべきか判断できない。

SNI は平文で流れる。そのため通信内容は暗号化されていても、 「どのサイトに接続しているか」は経路上から観測できる。 これはプロキシやファイアウォールがSNIを見てURLフィルタリングを行えるという 運用上の利点でもあり、同時にプライバシー上の課題でもある（ECH による暗号化の動きがある）。 第13章のSWG／URLフィルタリングと直結する論点。

8.6SSL-VPN 頻出

SSL-VPNは、TLSを使ったリモートアクセスVPN。 在宅勤務・外出先からの社内アクセスで用いる。実現方式は3つあり、 「通せる通信の範囲」と「クライアントに必要なもの」がトレードオフになっている。

IPsec-VPN と SSL-VPN の比較 頻出
IPsec-VPNSSL-VPN
主な用途拠点間の常時接続個人端末からのリモートアクセス
動作層L3（IP層）L4〜L7（TLS）
クライアント専用装置または専用ソフトが必要方式による。リバースプロキシ型ならブラウザだけ
通せる通信IPユニキャスト全般（設定した範囲）方式による。狭い〜広い
経路上の通過性NAT越えにNAT-Tが必要。UDP500/4500 の許可も要るTCP 443 を使うため、多くの環境でそのまま通る
アクセス制御アドレス・ポート単位利用者単位・アプリケーション単位で細かく制御しやすい
■ 午後での問われ方
  • SSL-VPNを選ぶ理由 → 「TCP 443 を使うため、訪問先やホテルなど接続元の環境を問わず利用できる可能性が高く、 端末への専用ソフト導入も最小限で済むため」
  • リバースプロキシ型の制約 → Webアプリケーション以外は利用できない
  • リモートアクセスVPNの認証強化 → ID／パスワードに加え、クライアント証明書やワンタイムパスワードによる 多要素認証（第12章）

8.7SSLオフロードと SSL可視化 頻出

暗号化された通信を途中の機器がいったん復号するという点では同じだが、目的が正反対である。

SSL可視化の課題 頻出

  • プライバシーと法的配慮：私的な通信の内容まで見えてしまうため、利用規程での明示と同意が必要。 銀行・医療など特定カテゴリは復号対象から除外する運用が一般的
  • 証明書ピンニングを行うアプリは失敗する：あらかじめ特定の証明書のみを信頼するよう作られたアプリは、 差し替えられた証明書を拒否して通信できなくなる。例外リストによる除外が必要
  • 処理性能：復号・再暗号化は重い処理であり、機器のスループットがボトルネックになりやすい
  • QUIC（HTTP/3）への未対応：復号できないため、UDP443を遮断してTCPへフォールバックさせる運用がとられる（第4章）
■ 午後での問われ方
  • SSLオフロードの目的 → 「Webサーバの暗号化処理の負荷を軽減し、 併せて復号後の内容を用いたL7での振分けやCookieによるセッション維持を可能にするため」
  • SSL可視化の必要性 → 「通信が暗号化されているとIPS・WAF・URLフィルタが内容を検査できず、 マルウェアの侵入や情報の持ち出しを検知できないため」
  • SSL可視化の導入時に必要な準備 → 内部CAのルート証明書を全端末に配布すること
