5.1DHCP の基本動作 頻出

DHCP（Dynamic Host Configuration Protocol）は、 IPアドレスだけでなくサブネットマスク・デフォルトゲートウェイ・DNSサーバなど、 通信に必要な設定一式を自動配布するプロトコル。 サーバが UDP 67番、クライアントが UDP 68番を使う。

リース期間と更新 頻出

払い出したアドレスにはリース期間が設定される。クライアントは満了を待たず、途中で更新を試みる。

  • T1（リース期間の50%）：元のサーバへユニキャストで REQUEST を送り、更新を求める。成功すれば ACK が返り、期間がリセットされる（DORA全体はやり直さない）
  • T2（リース期間の87.5%）：T1で応答がない場合、ブロードキャストで REQUEST を送り、どのサーバでもよいので更新を求める
  • 満了：それでも応答がなければアドレスを手放し、DISCOVER からやり直す

リース期間の設計は「短くすると再利用効率が上がるがトラフィックと負荷が増える」「長くすると アドレスが解放されず枯渇しやすい」というトレードオフになる。 来客用の無線LANのように入れ替わりが激しい環境では短く設定する、というのが定番の解答。

スコープ・除外・予約

  • スコープ：払い出すアドレスの範囲。通常はサブネットごとに定義する
  • 除外アドレス：スコープ内でも配らないアドレス。ルータ、サーバ、プリンタなど静的に設定した機器と重複させないために設ける
  • 予約（固定割当）：MACアドレスと結びつけて、常に同じIPアドレスを払い出す。 静的設定と違い、設定情報の管理をDHCPサーバに一元化したままアドレスを固定できるのが利点

5.2DHCPリレーエージェントとオプション 頻出

なぜリレーエージェントが必要か

DISCOVER はブロードキャストであり、ルータを越えない。 そのため、セグメントごとにDHCPサーバを置かない限り、そのままでは届かない。 DHCPリレーエージェントは、ルータ／L3スイッチが 受け取ったブロードキャストをユニキャストに変換してDHCPサーバへ転送する機能である。

記述の型。「DHCPサーバを各拠点に置かず集約する場合に必要な設定は何か」→ 「各セグメントのルータ（L3スイッチ）に DHCPリレーエージェントを設定し、DHCPサーバのIPアドレスを指定する」。 さらに理由を問われたら「DHCPのDISCOVERはブロードキャストでありルータを越えられないため」と書く。

不正DHCPサーバ対策 頻出

利用者が持ち込んだ無線ルータなどが意図せずDHCPサーバとして応答してしまうと、 誤ったデフォルトゲートウェイやDNSサーバが配られ、通信不能や中間者攻撃につながる。 DHCPは「先に応答したものが採用される」ため、正規サーバより速く応答されると防げない。

対策が DHCPスヌーピング。スイッチのポートを信頼ポート／非信頼ポートに分け、 非信頼ポートから届いた OFFER・ACK（サーバからのメッセージ）を破棄する。 正規のDHCPサーバが接続されている側のポートだけを信頼ポートに設定する。

DHCPスヌーピングの副産物 ― バインディングテーブル

スヌーピングの過程でスイッチは「MACアドレス・IPアドレス・接続ポート・VLAN」の対応表を作る。 この表を使って、Dynamic ARP Inspection（不正なARP応答の遮断＝ARPスプーフィング対策）や IPソースガード（送信元IP詐称の遮断）を実現できる。 DHCPスヌーピングが他のセキュリティ機能の土台になるという点が問われる。

■ 午後での問われ方
  • 端末に 169.254.x.x が付いている → DHCPサーバに到達できていない。 リレーエージェントの設定漏れ、VLAN誤設定、スコープ枯渇を疑う
  • DHCPサーバを冗長化する方法 →スコープを分割して2台に分ける（例：前半・後半で分担）、 またはサーバ間でリース情報を同期させる構成。同じ範囲を2台に設定すると重複払出しが起きる
  • フリーアドレス化で「席を移動しても同じ設定が使えるようにする」→ DHCPによる集中管理の利点

5.3DNS の構造とサーバの役割分担 最重要

DNS は、ドメイン名（FQDN）と IPアドレスなどの情報を対応づける、 世界規模の分散データベース。単一の巨大な表を持つのではなく、 階層ごとに管理を委任することで規模と自律性を両立している。

権威サーバとキャッシュサーバを分離する理由 頻出

  • 役割が真逆：権威サーバは外部の不特定多数から問い合わせを受ける。 キャッシュサーバは内部の利用者のためだけに再帰問い合わせを行う
  • 1台に同居させると、外部から再帰問い合わせを受け付けてしまう（オープンリゾルバ）危険がある
  • キャッシュポイズニングの成功時に、権威サーバの正しい情報まで巻き添えになるのを防げる
  • キャッシュサーバの過負荷が、自社ドメインの名前解決（＝外部からの到達性）に影響しない

5.4名前解決フロー 最重要

この節が書ければ DNS の設問はほぼ取れる。問い合わせには2種類あり、誰が誰に投げるかで決まっている。

  • 再帰問い合わせ：「最終的な答えが出るまで面倒を見てくれ」という依頼。 スタブリゾルバ → フルサービスリゾルバの1回だけ
  • 反復問い合わせ：「あなたが知っていることだけ答えてくれ」という問い合わせ。 フルサービスリゾルバ → 各階層の権威サーバ。答えを知らないサーバは「次はここに聞け」という 委任情報（NSレコード）を返す

キャッシュの効き方 ― 途中階層も効く

キャッシュされるのは最終回答だけではない。「jp の権威サーバはここ」「co.jp の権威サーバはここ」という 委任情報もキャッシュされる。そのため www2.example.co.jp を次に引くときは、 ルートや jp へは問い合わせず、example.co.jp の権威サーバへ直接聞きに行ける。

DNSフォワーダは、フルサービスリゾルバが自分で反復問い合わせをせず、 上位の別のキャッシュサーバへ転送して答えをもらう設定。 支店のDNSサーバを本社のDNSサーバに向ける、社内サーバをISPのサーバに向ける、といった構成で使う。 キャッシュを集約でき、外部へ直接問い合わせる機器を限定できる（＝ファイアウォールの穴を減らせる）のが利点。

■ 午後での問われ方
  • 「PCが行う問い合わせ」と「DNSサーバが行う問い合わせ」の名称をそれぞれ答えよ → 再帰／反復
  • キャッシュサーバを設置する目的 → 「同じ問い合わせに対して外部への問い合わせを省略でき、 応答時間の短縮と外部回線・上位サーバの負荷軽減が図れるため」
  • ファイアウォールの通過設定 → キャッシュサーバからの外向き UDP/TCP 53 を許可し、 それ以外の端末からの直接の外部DNS問い合わせは遮断する（マルウェアの通信抑止にもなる）

5.6可用性と設計手法 頻出

DNSラウンドロビン

同じ名前に対して複数のAレコードを登録し、問い合わせのたびに順序を入れ替えて返すことで、 アクセスを複数のサーバへ分散させる簡易な負荷分散。装置を追加せずに実現できるのが利点。

ラウンドロビンの限界 ― 負荷分散装置との比較
観点DNSラウンドロビン負荷分散装置（LB）
サーバ障害検知できない。停止中のサーバのIPも返し続けるヘルスチェックで自動的に切り離す
負荷の偏りキャッシュにより偏る。実際の負荷は見ていない接続数・応答時間に応じて振り分けられる
セッション維持できない可能（第9章）
コストほぼゼロ装置費用・設計工数が必要
記述の定番。「DNSラウンドロビンの問題点を述べよ」→ 「サーバの稼働状態を監視していないため、障害が発生したサーバのIPアドレスも応答として返してしまい、 一部の利用者が接続できなくなる」。さらに「キャッシュのTTLが切れるまで振分けが変わらない」も加点要素。

GSLB（広域負荷分散）

GSLB（Global Server Load Balancing）は、 DNSの応答を動的に変えることで、地理的に離れた複数サイトへ振り分ける仕組み。 ラウンドロビンと違い、各サイトの死活・負荷・クライアントからの距離を考慮して返すIPを決める。

  • 災害対策（DR）：平常時はメインサイトのIPを返し、障害時は自動的にバックアップサイトのIPを返す
  • 拠点最適化：利用者に最も近いデータセンタへ誘導し、遅延を減らす
  • 弱点：キャッシュのTTLが残っている間は古いIPが使われ続けるため、切替が即時にならない。 そのためGSLB用のレコードはTTLを極端に短く設定する

DNSスプリット（内部／外部分離） 最重要

■ 午後での問われ方
  • 内部DNSと外部DNSを分ける理由 → 「外部DNSには公開サーバの情報だけを登録し、 内部のホスト名やプライベートIPアドレスといった内部構成情報が外部から取得されないようにするため」
  • DR切替の手順 → 「事前に該当レコードのTTLを短縮しておき、切替時にAレコードを バックアップサイトのIPアドレスへ変更する」（GSLBならその自動化）
  • 切り替えたのに一部の利用者が旧サーバへ行く → キャッシュサーバに旧レコードがTTLの間残っているため

5.7DNS セキュリティ 頻出

DNSキャッシュポイズニング

正規の権威サーバより先に、偽の応答をキャッシュサーバへ送り込み、 誤ったIPアドレスをキャッシュさせる攻撃。成功すると、利用者は正規のURLを入力しているのに 偽サイトへ誘導される（フィッシング、マルウェア配布）。

カミンスキー攻撃 頻出

通常のキャッシュポイズニングは、正規の答えがキャッシュされてしまうとTTLが切れるまで再挑戦できない。 カミンスキー攻撃はこの制約を破る手法で、random1.example.co.jp、 random2.example.co.jp …と存在しない名前を次々問い合わせさせる。 存在しない名前はキャッシュにないため、キャッシュサーバは毎回外部へ問い合わせざるを得ず、 攻撃者は何度でも偽装を試行できる。

さらに偽装する対象を「そのホストのAレコード」ではなく「ゾーン全体の委任情報（NSレコードとグルーレコード）」 にすることで、成功すればドメイン配下すべての名前解決を乗っ取れる。

DNSSEC 頻出

DNSSECは、DNS応答にディジタル署名を付け、 「正しい権威サーバが出した、改ざんされていない情報である」ことを検証できるようにする拡張。

最重要の注意点：DNSSEC は暗号化しない。 保証するのは完全性（改ざんされていないこと）と出自の認証であって、 通信内容の秘匿（盗聴防止）ではない。問い合わせ内容は平文のまま流れる。 盗聴を防ぎたい場合は DNS over TLS / HTTPS を使う。ここは選択肢問題で必ず狙われる。

ルートゾーンを起点に ルート → TLD → 各ゾーンと DS レコードで鍵をたどれることを 信頼の連鎖（chain of trust）と呼ぶ。どこか1つでもDNSSEC未対応だと連鎖が切れて検証できない。

署名の付いた応答はサイズが大きくなり UDPの512バイト制限を超えるため、 EDNS0差がつく（UDPで大きな応答を扱えるようにする拡張）が前提となる。

オープンリゾルバと DNSアンプ攻撃 頻出

オープンリゾルバとは、誰からの再帰問い合わせにも応答してしまうDNSサーバ。 設定ミスや、権威サーバとキャッシュサーバを同居させたことが原因で生まれる。

これを踏み台にするのが DNSアンプ攻撃（DNSリフレクション／増幅攻撃）。 送信元IPアドレスを標的に詐称した小さな問い合わせを大量に送り、 大きな応答を標的へ集中させる。問い合わせに対して応答が数十倍の大きさになるため、 攻撃者は少ない帯域で大量のトラフィックを標的に浴びせられる。

対策の書き方

  • 自サーバを踏み台にしない：再帰問い合わせを受け付ける範囲を、自組織の内部アドレスに限定する
  • 権威サーバでは再帰問い合わせを無効にする
  • 送信元詐称そのものを防ぐ：ISP・組織の出口で Ingressフィルタリング（BCP38）／uRPF を実施する（第13章）
  • 応答レート制限（RRL）で同一宛先への大量応答を抑制する
