第17章　マルチキャスト IP Multicast

「同じデータを、複数の相手へ、1回の送信で届ける」ための仕組み。 鍵になるのは「誰が受け取りたいのかを、ネットワークがどうやって知るか」という一点である。 端末とルータの間でそれを伝えるのが IGMP、 L2スイッチがそれを盗み見て学習するのが IGMPスヌーピング、 ルータ間で配送ツリーを作るのが PIM——役割分担で整理すると迷わない。

17.3IGMP ― 端末とルータの間 頻出

IGMP（Internet Group Management Protocol）は、 端末が「このグループを受信したい」とルータに伝えるためのプロトコル。 役割は端末〜最寄りのルータ間に限定される——ルータどうしの配送はPIMの仕事である。

IGMP のバージョン
版特徴
IGMPv2Leave Group による明示的な離脱通知が加わり、離脱の検知が速くなった。 グループ単位での参加（誰が送信してもよい）
IGMPv3 差がつく 受信したい送信元を指定できる（Source-Specific）。 「グループGを、送信元Sからだけ受信する」と要求できるため、 意図しない送信元からの配信を受け取らずに済み、RPを必要としないSSMの基盤になる

17.4IGMPスヌーピング 頻出

なぜ必要か

L2スイッチはMACアドレステーブルを「受信フレームの送信元MAC」から学習する（第2章）。 ところがマルチキャストMACアドレスは送信元として現れないため、テーブルに載らない。 その結果、スイッチはマルチキャストフレームをブロードキャストと同様にフラッディングしてしまう。

IGMPクエリア 頻出

IGMPスヌーピングは、ルータが定期的に送る Membership Query と、それに対する Report を観測して 参加ポートを学習する。したがってQuery が流れてこないと、学習した情報がタイムアウトして消えてしまう。

問題が起きるのは、そのセグメントにマルチキャスト対応のルータが存在しない場合—— たとえば配信サーバと受信端末が同一セグメント内にあり、L2スイッチだけで完結している構成。 このとき、スイッチのいずれか1台を IGMPクエリア として動作させ、 代わりに Query を送出させる必要がある。

典型的な障害シナリオ。 「マルチキャスト配信が、最初は正常だが数分後に途切れる（またはフラッディングし始める）」—— これはQuery が流れずスヌーピングのテーブルがタイムアウトしたことを示す。 対策はクエリアの設定。ルータのない環境で必ず問われるポイント。
■ 午後での問われ方
  • IGMPスヌーピングを有効にする理由 → 「L2スイッチはマルチキャストフレームを全ポートに フラッディングしてしまうため、受信を要求していない端末にも配信され、帯域と端末の処理負荷を浪費するから」
  • クエリアが必要な場面 → そのVLANにマルチキャストルータが存在しない場合
  • スヌーピングはどの層の情報を見ているか → L2スイッチがL3のIGMPメッセージを参照している

17.5PIM ― ルータ間の配送 頻出

PIM（Protocol Independent Multicast）は、 ルータどうしでマルチキャストの配送ツリーを構築するプロトコル。 「Protocol Independent」とは、既存のユニキャストのルーティングテーブルを利用するため、 OSPFでもBGPでも何を使っていてもよいという意味である。

RPF ― マルチキャストのループ防止 頻出

RPF（Reverse Path Forwarding）は、 受信したマルチキャストパケットについて「送信元アドレスへ戻る最短経路のインタフェースから届いたか」を 検査し、違うインタフェースから来たものは破棄する仕組み。 マルチキャストは複製されて広がるため、これがないとループしたパケットが指数的に増殖する。 第3章の uRPF と同じ「送信元アドレスを逆引きして妥当性を確かめる」という考え方である。

17.6設計上の注意

導入時に確認すること
観点内容
経路上の全機器送信元から受信者までのすべてのスイッチ・ルータがマルチキャストに対応し、 適切に設定されている必要がある。1台でも未対応・未設定の機器があるとそこで止まる
WAN区間IP-VPNなどの事業者網でマルチキャストが利用できるとは限らない。 利用できない場合は、GREでカプセル化してユニキャストとして通す（第8章）、 あるいは拠点ごとに配信サーバを置くといった代替設計が必要になる
無線LANマルチキャストは最も低い速度で送信されるため、 無線区間では効率が悪く、他の通信を圧迫する。 APでユニキャストへ変換する機能を使うか、無線区間では使わない設計にする
帯域設計配信するストリーム数×ビットレートで所要帯域を算出する。 受信者が増えても帯域は増えないのがマルチキャストの利点だが、 配信するチャネル数が増えれば帯域も増える
アドレス設計17.2節のとおり、下位23ビットの衝突を避けるようグループアドレスを計画する
「ブロードキャスト抑制」との違いに注意。 ストームコントロール（第2章）のブロードキャスト抑制は、 閾値を超えたブロードキャストを破棄して帯域を守る機能であり、マルチキャストとは別物。 ただしストームコントロールの対象に「未知のマルチキャスト」を含める設定をしていると、 正規のマルチキャスト配信まで破棄されることがある——という形で組み合わせて問われることがある。
■ 午後での問われ方（総まとめ）
  • マルチキャストを採用する理由 → 「受信者数が増えても配信サーバの送出データ量と 上流の帯域が増えないため、多数の拠点・端末へ同一の映像を配信するのに適しているから」
  • 役割分担 → IGMP＝端末とルータの間／IGMPスヌーピング＝L2スイッチの転送先の絞り込み／ PIM＝ルータ間の配送ツリー構築
  • 配信が途中から途切れる／フラッディングし始める → IGMPクエリアが不在で スヌーピングのテーブルがタイムアウトした
  • RPが必要な理由と不要にする方法 → 送信元と受信者の待ち合わせ場所として必要。 IGMPv3によるSSMを使えば不要になる
  • マルチキャストがUDPである影響 → 再送されないため、パケットロスが映像の乱れとして直接現れる
