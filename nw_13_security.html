第13章　セキュリティ Network Security

長らく「境界を作り、そこで守る」という思想で組み立てられてきた領域。 その基本形がゾーニングとファイアウォールである。 しかしクラウド利用とリモートワークによって守るべき境界そのものが消えつつあり、 ゼロトラスト／SASE という新しい考え方が生まれた。 この思想の転換を説明できることが、近年の午後Ⅱでの得点源になる。

フィルタリングの方式

判断材料1パケットごとに、送信元／宛先IPアドレス、プロトコル、ポート番号を見る 上記に加え、コネクションの状態（3wayハンドシェイクの進行、どちら向きに始まった通信か）を記憶する

第3章の非対称経路と直結する。 ステートフルなFWは往路を見て状態を作るため、 復路が別のFWを通ると「状態表にない不正なパケット」として破棄される。 FWを冗長化する構成では、経路を対称にするか、機器間で状態情報を同期させる必要がある。

ACL の書き方 頻出

2つの原則

  • ルールは上から順に評価され、最初に一致したもので処理が確定する。 以降のルールは評価されないため、ルールの順序が結果を左右する。 広い許可を先に書いてしまうと、後ろの個別の拒否が効かなくなる
  • 暗黙のdeny：明示的に許可されていない通信はすべて拒否される。 つまり「必要なものだけを列挙して許可する」ホワイトリスト方式が基本になる

13.2検知・防御装置 頻出

IDS と IPS

検知方式
方式仕組み長所／短所
シグネチャ型
（不正検出）		既知の攻撃パターンと照合する 誤検知が少なく確実／シグネチャが未登録の未知の攻撃は検知できないため、定義ファイルの更新が不可欠
アノマリ型
（異常検出）		通常の通信の傾向を学習し、そこから逸脱した振る舞いを検知する 未知の攻撃にも対応できる／正常な業務の変化を攻撃と誤認しやすく、誤検知が多い

WAF 頻出

WAF（Web Application Firewall）は、 HTTPの中身（リクエストのパラメータ）を検査して、Webアプリケーションへの攻撃を防ぐ装置。

FW・IPS・WAF の守備範囲 頻出

  • ファイアウォール：「443番ポートを通すか通さないか」しか判断できない。 通した通信の中身は見ない
  • IPS：ネットワーク全般の既知の攻撃パターン（OSやミドルウェアの脆弱性を突く通信）を検知する
  • WAF：アプリケーションの入力値に着目する。 SQLインジェクション（データベースへの命令を紛れ込ませる）、 クロスサイトスクリプティング（他の利用者のブラウザで実行される script を埋め込む）など、 正規のHTTPリクエストの形をした攻撃を防ぐ
WAFはHTTPSを復号しないと機能しない。 暗号化されたままでは中身を検査できないため、 負荷分散装置でのSSLオフロード（第8章・第9章）の後ろに配置するか、 WAF自身がTLSを終端する構成にする必要がある。この配置の理由が設問になる。

サンドボックスは、受信したファイルを隔離された仮想環境で実際に実行し、 その挙動から悪意の有無を判定する仕組み。 シグネチャに存在しない未知のマルウェアを検知できるのが利点だが、 判定に時間がかかる、サンドボックスを検知して動作を止めるマルウェアがある、といった限界もある。

13.3プロキシサーバ 頻出

プロキシの3つの型
種別誰を代理するか目的
フォワード
プロキシ		内部の利用者が外部へアクセスするのを代理する ①アクセスログの取得（誰がいつどこへ）　②URLフィルタリング　③キャッシュによる帯域削減　 ④内部端末のアドレスを外部に見せない

透過型
プロキシ		経路上で自動的に処理する 端末側にプロキシの設定が不要。設定できない機器や、設定を回避されたくない場合に使う
関連するキーワード
用語内容
プロキシ認証プロキシ利用時にID／パスワードを要求する。アクセスログを利用者単位で記録できるようになり、 内部不正の抑止と追跡に効く
PACファイル宛先に応じてプロキシを使い分けるルールを記述したスクリプト。 「社内システムは直接、外部サイトはプロキシ経由」といった振り分けができる。 第7章のローカルブレイクアウトの実現手段の1つ
WPAD 差がつくPACファイルの場所をDHCPやDNSを使って自動的に発見する仕組み。 便利だが、攻撃者が偽のWPAD応答を返すと、通信を自分のプロキシへ誘導できてしまうという危険がある
URLフィルタリングカテゴリ（ギャンブル、不正サイト等）や個別URLで遮断する。 HTTPS通信ではURL全体は見えないため、TLSの SNI（第8章）でホスト名を判別するか、 SSL可視化により復号して判定する
■ 午後での問われ方
  • プロキシを経由させる理由 → 「利用者ごとのアクセスログを取得でき、 URLフィルタリングによって業務に不要なサイトやマルウェア配布サイトへの アクセスを遮断できるため」
  • 端末から直接インターネットへ出る通信をFWで遮断する理由 → プロキシを迂回されると ログも制御も効かなくなるため。マルウェアのC&C通信の抑止にもなる
  • リバースプロキシを置く理由 → 「Webサーバを直接外部に公開せず、 サーバのIPアドレスや構成を隠蔽できるため」

13.5ゼロトラストと SASE 頻出

なぜ境界型では足りなくなったのか

ゼロトラストを構成する技術 頻出
用語役割置き換わる従来技術
SWG
（Secure Web Gateway）		クラウド上のプロキシ。URLフィルタリング、マルウェア検査、 アプリケーション制御を行う社内に設置していたプロキシ。 社外にいる端末も同じポリシーで保護できるのが利点
ZTNA 頻出アプリケーション単位でアクセスを許可する。 利用者・端末を検証したうえで、その人に必要なアプリだけに接続させる リモートアクセスVPN。VPNは一度つなぐと社内ネットワークに広くアクセスできてしまうのに対し、 ZTNAは必要なアプリ以外は見えない
CASB 差がつくクラウドサービスの利用状況を可視化し、制御する。 会社が把握していないサービスの利用（シャドーIT）を発見できる—
SASE 頻出ネットワーク機能（SD-WAN）とセキュリティ機能（SWG／ZTNA／CASB／FWaaS）を クラウド上で統合して提供するという概念拠点ごとのUTM＋本社集約型の構成
マイクロ
セグメンテーション 差がつく		 サーバ間・仮想マシン間の通信を細かい単位で制御する。 「Webサーバ→APサーバの特定ポートのみ許可」といった粒度 ネットワーク境界のFWだけでは防げなかったデータセンタ内部の横展開を封じる
第7章のローカルブレイクアウトと必ずつながる。 拠点から直接インターネットへ出すと、本社のFW・プロキシによる保護が効かなくなる。 その穴を埋めるのがクラウド型のSWG／SASEである。 「回線設計の変更が、セキュリティ方式の変更を要求する」という因果を書けると評価が高い。
■ 午後での問われ方
  • ゼロトラストを採用する背景 → 「クラウド利用とテレワークの普及により、 守るべき資産と利用者が社内ネットワークの外に広がり、 境界での防御だけでは保護できなくなったため」
  • VPNからZTNAへ移行する理由 → 「VPNは接続後に社内ネットワーク全体へアクセスできてしまうのに対し、 ZTNAは利用者ごとに必要なアプリケーションのみへのアクセスに限定できるため」
  • マイクロセグメンテーションの目的 → 侵入された場合の横展開（ラテラルムーブメント）を防ぎ、 被害を局所化するため

13.6ログ管理と監視 頻出

監視・分析の仕組み
用語内容
SIEM 差がつく FW・プロキシ・サーバ・認証サーバなど、各所のログを一元的に集約し、 相関分析して脅威を検知する基盤。 単体のログでは異常に見えない事象も、組み合わせることで攻撃の兆候が浮かび上がる （例：認証失敗の多発 → 成功 → 大量のデータ送信）
EDR 差がつく 端末上の挙動を継続的に記録し、不審な動作を検知して対処する仕組み。 アンチウイルスが「侵入を防ぐ」のに対し、EDRは「侵入されたあとに気づいて対応する」ためのもの。 感染端末をネットワークから隔離する機能も持つ
ログ監査取得したログを定期的に点検し、不正の兆候や規程違反を発見する。 取得することと、見ることは別——ログを取っていても監査していなければ意味がない

ログ設計で押さえる3点 頻出

  • 時刻の一致：複数機器のログを突き合わせるには、すべての機器がNTPで時刻同期されていることが 絶対条件（第18章）。時刻がずれていると事象の前後関係が追えず、証跡として使えない
  • 保存期間と容量：インシデントは発生から発覚まで数か月かかることも珍しくないため、 調査に足る期間を保存する。容量とコストの設計が必要
  • 改ざん防止：侵入者は痕跡を消そうとするため、 ログを機器のローカルではなく別のログサーバへ転送し、書換えできないよう保護する（第18章のSyslog）
NAT環境でのログ追跡（第6章の再掲）。 NAPTにより多数の利用者が同一のグローバルアドレスを共有するため、 外部のログだけでは発信者を特定できない。 NAT機器側で「時刻・変換前アドレス・変換後のポート番号」を記録し、 かつ時刻が同期されていること——この2つが揃って初めて追跡が成立する。
■ 午後での問われ方
  • ログサーバへ集約する理由 → 「機器の故障や侵入者による改ざんからログを保護し、 複数機器のログを横断して分析できるようにするため」
  • NTP同期が必要な理由 → 「複数の機器のログを時系列で突き合わせて事象を追跡するため」
  • プロキシのログで検知できること → マルウェアに感染した端末からC&Cサーバへの 定期的な通信（不審な宛先への繰り返しアクセス）
